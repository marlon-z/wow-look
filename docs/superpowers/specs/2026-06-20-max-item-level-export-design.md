# WoWLook 最高可获得装等导出设计

日期：2026-06-20  
状态：已批准并实施  
目标分支：`feat/max-item-level-export`

## 1. 背景

`WoWLookExport3` 当前以游戏内冒险指南为数据源，扫描当前赛季地下城和团本掉落，并直接读取冒险指南返回的 `displayLink`。这条链路能够准确回答：

- 当前赛季有哪些地下城和团本；
- 每件装备由哪个副本、哪个首领掉落；
- 装备适用的职业和专精；
- 冒险指南当前展示档位下的名称、属性和说明框内容。

当前不足是：冒险指南返回的装备链接通常代表掉落档位或当前难度展示档位，不代表该装备沿实际升级轨道能够达到的最高装等。因此，现有导出中会同时出现 246、263、269、276、285 等装等，无法按最高可获得状态统一展示和比较。

KeystoneLoot 证明了一条可行路径：保留装备 ID，通过赛季升级轨道、目标装等和 Bonus ID 构造新的装备链接，再让游戏客户端解析该链接的最终说明框。

本设计只借鉴这套链接构造思路，不把 KeystoneLoot 作为 WoWLook 的运行时依赖，也不替换 WoWLook 现有的掉落数据源。

## 2. 目标

本次改造需要实现：

1. 继续以冒险指南作为当前赛季掉落关系的事实来源。
2. 为每件装备判断其实际可获得的最高升级轨道。
3. 构造该最高轨道最终档位对应的装备链接。
4. 从最高档链接读取装等、主副属性、耐力、护甲、武器伤害、装备特效和使用特效。
5. 同时保留原始掉落档位数据，保证结果可追溯。
6. 生成失败时明确标记，禁止把原始低装等结果伪装成最高档结果。
7. 将赛季变化集中到独立配置文件，尽量避免下赛季修改主扫描逻辑。

## 3. 非目标

本次不做以下事情：

- 不导入或复制 KeystoneLoot 的完整装备数据库。
- 不要求用户安装 KeystoneLoot。
- 不改变地下城、团本和首领的发现方式。
- 不改变职业、专精归属的现有扫描方式。
- 不负责制造业装备、世界任务装备、PvP 装备等当前范围外的数据。
- 不尝试通过网络在游戏内自动下载赛季配置。
- 不在本次改造中调整小程序界面设计。

## 4. 最高装等口径

“最高装等”定义为：同一装备在当前赛季规则下，通过其实际存在的获取来源和升级轨道，能够合法达到的最高档位。

具体规则：

- 大秘境装备：按该地下城装备能够通过宏伟宝库获得的最高轨道最终档位计算。
- 团本装备：按该装备实际存在的最高团本难度及其升级轨道最终档位计算。
- 同一装备有多个来源：分别计算候选最高档，选择装等最高且验证成功的结果。
- 不可升级装备：保留其最高实际掉落版本，不强行套用升级轨道。
- 特殊团本、稀有掉落、固定装等装备：通过独立规则覆盖通用逻辑。
- 当前赛季所有武器槽和饰品槽装备：在正常来源规则确定后改用虚空铸造史诗链接模板，目标装等 298。
- 其他装备的目标值由当前赛季普通升级轨道配置决定，当前为 289。

这个口径与“把所有装备强行改成相同装等”不同。后者虽然实现简单，但可能生成游戏中无法获得的装备状态，因此不采用。

## 5. 方案选择

### 5.1 方案 A：所有装备强制到一个目标装等

优点：实现简单，适合纯数值横向比较。  
缺点：忽略装备真实轨道，可能生成不可获得状态。  
结论：不采用。

### 5.2 方案 B：独立赛季配置 + 实际来源判定 + 游戏内验证

优点：符合真实获取规则；保持现有数据链路；每个赛季主要更新配置。  
缺点：需要维护轨道 Bonus ID，并处理少量特殊装备。  
结论：采用。

### 5.3 方案 C：完全通过游戏 API 自动发现升级规则

优点：理论上减少人工配置。  
缺点：现有 API 不能稳定、完整地提供“来源到最高轨道”的全部映射，特殊物品仍需规则；版本变化时难以排错。  
结论：不采用。

## 6. 总体架构

改造后的链路：

```text
冒险指南扫描
    ↓
掉落索引（装备 ID、实例、首领、难度）
    ↓
原始展示链接解析
    ↓
根据来源选择最高可获得轨道
    ↓
SeasonConfig + Bonus ID 构造最高档链接
    ↓
游戏 API 验证目标装等
    ↓
读取最高档 Tooltip
    ↓
导出原始档位 + 最高档位 + 验证状态
```

现有的“赛季实例识别、首领掉落索引、职业专精补采”保持不变。新增逻辑位于 `ResolveItemDisplayLink` 与 `FillItemDetails` 之间，形成独立的“最高档链接生成与验证层”。


示例中的 `targetItemLevel` 和 Bonus ID 只是结构示意，实施时必须以当前正式服验证结果填写，不能直接使用占位值。

### 7.2 `WoWLookExport3.lua`

主文件新增以下职责明确的函数，避免将赛季规则散落在扫描逻辑中：

- `ValidateSeasonConfig()`：检查配置完整性和客户端版本。
- `SelectMaxUpgradeRule(item)`：根据装备来源选择最高轨道规则。
- `BuildMaxLevelItemLink(item, rule)`：生成候选最高档链接。
- `ValidateMaxLevelItemLink(item, link, rule)`：验证实际装等和装备身份。
- `ResolveMaxLevelLinks(itemsById)`：批量处理并收集成功、失败统计。
- `CaptureItemVersion(link)`：复用现有 Tooltip 采集和结构化解析。

主文件现有扫描职责不改变。

### 7.3 `WoWLookExport3.toc`

加载顺序调整为：

```text
SeasonConfig.lua
WoWLookExport3.lua
```

## 8. 最高档链接生成

### 8.1 输入

每件装备至少需要：

- `itemId`；
- 原始冒险指南 `displayLink`；
- `sources`；
- 装备类别和部位；
- 当前客户端可解析的基础装等。

### 8.2 通用规则

通用装备链接由以下信息组成：

1. 装备 ID；
2. 目标装等相对基础装等的调整 Bonus ID；
3. 目标升级轨道 Bonus ID；
4. 必需的品质 Bonus ID；
5. 戒指、项链等赛季特定 Bonus ID；
6. 装备特有的 Bonus ID；
7. 当前角色等级和一个对该装备有效的专精 ID。

装等调整 Bonus ID 映射属于链接生成基础设施，不等同于赛季配置。首次实现可以采用经过验证的完整映射；以后只有出现无法覆盖的新差值时才扩展，不要求每个赛季重写整张表。

### 8.3 原始链接处理

原始 `displayLink` 必须保留在导出数据中，但最高档链接不应直接无条件继承全部原始 Bonus ID。原始链接可能已经包含较低档装等或轨道 Bonus ID，和新规则叠加后会产生冲突。

实施时采用确定性重建：

- 以 `itemId` 为基础生成新链接；
- 加入当前目标轨道所需的 Bonus ID；
- 通过 `specialItems` 显式补充需要保留的装备特有 Bonus ID；
- 不明 Bonus ID 不自动混入最高档链接；
- 生成后必须由游戏客户端验证。

### 8.4 专精选择

构造链接时优先使用该装备 `specsByClass` 中当前角色可用的专精。如果当前角色不适用，则选取装备记录中的第一个有效专精。无法确定有效专精时，标记失败，不使用随机专精生成正式数据。

## 9. 来源到最高轨道的判定

### 9.1 大秘境

当前赛季地下城掉落池中的装备，以宏伟宝库可提供的最高轨道最终档作为最高候选。原始副本掉落链接继续保留，用于说明实际来源和掉落档位。

### 9.2 团本

团本装备按该装备在冒险指南中实际存在的最高难度计算。只有当装备确实存在于该难度掉落表中时，才能应用该难度对应的最高轨道。

不能简单地因为装备来源是团本，就默认它具有史诗难度版本。

### 9.3 多来源装备

同一 `itemId` 若来自多个副本或多种内容：

1. 为每个来源产生候选规则；
2. 按候选目标装等从高到低验证；
3. 使用第一个验证成功的候选；
4. 保留所有原始 `sources`。

### 9.4 特殊规则

以下情况进入配置覆盖：

- 固定装等且不走常规升级轨道的装备；
- 特殊团本或特殊难度；
- 稀有掉落的额外装等规则；
- 需要额外 Bonus ID 才能保留正确效果的装备；
- 游戏客户端明确判定不可升级的物品。

特殊规则应尽量按来源或物品 ID 精确匹配，禁止使用宽泛规则影响整个掉落池。

### 9.5 武器与饰品虚空铸造 298 规则

当前赛季所有武器槽和饰品槽装备都可以通过虚空铸造史诗链路达到 298。它不是普通神话 6/6 轨道；不能把目标装等改成 298 后继续使用 `12806`，否则客户端只会解析为 289。

虚空铸造链接使用物品上下文 `35`，公共 Bonus ID `13440`、`6652` 和史诗标记 `13654`。饰品额外使用 `12699`，武器额外使用 `12701`。这些参数来自客户端背包中真实的 298 装备链接，包括物品 `193718`：

```text
item:193718::::::::90:270::35:4:13440:6652:12699:13654
```

规则在正常来源判定之后应用；不可升级名单和固定团本来源仍具有更高优先级。客户端必须同时验证物品身份、槽位和装等 298，否则按失败处理，禁止回退后伪装成功。

## 10. 导出数据结构

为减少前端改动，现有顶层展示字段继续代表最高档版本，同时新增明确的版本信息。

建议结构：

```json
{
  "itemId": 123456,
  "itemLevel": 298,
  "link": "最高档装备链接",
  "upgradeTrack": "神话 6/6",

  "dropVersion": {
    "itemLevel": 269,
    "link": "冒险指南原始链接",
    "upgradeTrack": "英雄 3/6"
  },

  "maxVersion": {
    "status": "ok",
    "itemLevel": 298,
    "link": "最高档装备链接",
    "track": "myth",
    "rank": 6,
    "ruleSource": "dungeon_great_vault"
  }
}
```

现有 `primaryStats`、`secondaryStats`、`stamina`、`effects`、`tooltip` 等字段均使用最高档链接解析结果。

若最高档生成失败：

- `maxVersion.status` 写入具体失败状态；
- `dropVersion` 仍完整保存；
- 顶层不得伪装成最高档成功结果；
- 转换脚本默认不把失败记录发布为正式最高装等数据。

## 11. 状态与错误处理

至少定义以下状态：

- `ok`：最高档链接和目标装等验证成功。
- `season_config_invalid`：赛季配置缺失或字段无效。
- `season_build_mismatch`：客户端版本超出配置声明范围。
- `no_upgrade_rule`：找不到适用轨道。
- `invalid_specialization`：无法选择有效专精。
- `base_item_level_unavailable`：无法取得基础装等。
- `bonus_mapping_missing`：目标差值没有对应 Bonus ID。
- `item_identity_mismatch`：新链接解析出的装备 ID 不一致。
- `target_item_level_mismatch`：实际解析装等不等于目标装等。
- `tooltip_unavailable`：链接有效但 Tooltip 尚未加载完成。
- `special_rule_required`：通用规则失败，需要增加精确覆盖。

任何失败都进入导出摘要，包含装备 ID、名称、来源、预期装等、实际装等和所用规则。

## 12. 异步加载与缓存

新生成的装备链接可能尚未进入客户端物品缓存。最高档处理沿用现有延迟完成机制，并增加：

- 对候选链接调用物品数据请求；
- 等待物品数据可用事件或有限次数重试；
- 按链接缓存 Tooltip 结果，避免重复解析；
- 设置总超时，超时后输出明确失败状态；
- 不因单件装备失败终止整批导出。

## 13. 验证策略

### 13.1 配置验证

导出开始前检查：

- 赛季配置存在；
- 当前客户端 Build 不低于配置要求；
- 目标装等、轨道 Bonus ID 为有效数字；
- 必需的装等差值映射存在；
- 特殊规则之间没有冲突。

### 13.2 单件验证

每件装备的最高档链接必须通过：

1. 链接能够被 `C_Item`/`GetItemInfo` 解析；
2. 解析出的装备 ID 与原装备一致；
3. `C_Item.GetDetailedItemLevelInfo(link)` 等于规则目标装等；
4. Tooltip 中解析出的装等与 API 结果一致；
5. 装备类型和部位没有发生异常变化；
6. Tooltip 关键字段可读取。

### 13.3 全量验证

导出完成后生成摘要：

- 总装备数；
- 最高档成功数；
- 各失败状态数量；
- 地下城/团本分别的成功率；
- 实际最高装等分布；
- 轨道分布；
- 特殊规则命中数量。

正式数据发布条件建议为：

- 配置验证通过；
- `target_item_level_mismatch` 为 0；
- `item_identity_mismatch` 为 0；
- 普通装备最高档成功率为 100%；
- 所有例外均有可解释的精确规则。

## 14. 测试计划

### 14.1 链接生成测试

至少选取：

- 一件地下城布甲；
- 一件地下城武器；
- 一件地下城饰品；
- 一件团本普通装备；
- 一件团本稀有装备；
- 一件戒指；
- 一件项链；
- 一件不可升级装备；
- 一件需要特殊 Bonus ID 的装备。

逐件核对装备 ID、目标装等、轨道、主副属性和特效文本。

武器和饰品预期使用包含 `13654` 的虚空铸造链接并解析为 298；普通护甲预期保持其正常最高轨道（当前为 289）。

测试至少抽查一个真实饰品（例如 `193718`）和一个真实武器，确认饰品链接包含 `12699`、武器链接包含 `12701`，两者都包含 `13440`、`6652`、`13654` 且上下文为 `35`。

### 14.2 回归测试

确认改造后：

- 当前赛季实例数量不变；
- 装备总数和来源关系不因最高档处理丢失；
- 职业/专精归属不变；
- `dropVersion` 与改造前原始输出一致；
- 转换脚本仍能按 13 个职业生成数据；
- 小程序现有筛选字段保持兼容。

### 14.3 故障测试

主动测试：

- 删除轨道 Bonus ID；
- 设置错误目标装等；
- 设置错误客户端 Build；
- 为特殊装备移除覆盖；
- 模拟 Tooltip 缓存未完成。

插件必须输出明确状态，而不是回退并标记成功。

## 15. 下赛季维护流程

新赛季更新时执行：

1. 确认正式服赛季最高轨道、最终档位和目标装等。
2. 更新 `SeasonConfig.lua` 中的赛季 ID、Build、轨道 Bonus ID 和目标装等。
3. 更新新增的槽位规则、特殊来源和特殊装备规则。
4. 运行少量代表性装备验证。
5. 运行 `/wowlook` 全量导出。
6. 检查最高档成功率、装等分布和失败清单。
7. 通过本地转换脚本生成并审核发布数据。

正常情况下，新赛季只修改配置和少量例外，不修改主扫描架构。普通补丁若未改变升级系统，则不需要更新配置；若暴雪调整轨道或特殊装备规则，则按验证结果更新。

## 16. 实施阶段划分

审核通过后，实施按以下顺序进行：

1. 建立独立赛季配置和配置校验。
2. 实现装等差值 Bonus ID 映射及确定性链接构造。
3. 实现来源到最高轨道的选择。
4. 实现最高档链接的异步加载和验证。
5. 重构单件 Tooltip 采集，使原始档和最高档复用同一解析函数。
6. 扩展导出结构和摘要。
7. 调整本地转换脚本，兼容 `dropVersion`/`maxVersion`。
8. 完成代表性装备测试和全量导出验证。

## 17. 验收标准

本功能完成需同时满足：

- WoWLook 不依赖 KeystoneLoot 安装或加载；
- 掉落范围、来源、职业和专精信息保持准确；
- 每件可升级装备输出实际可获得的最高轨道版本；
- 最高档 API 装等与 Tooltip 装等一致；
- 原始掉落版本完整保留；
- 所有失败可定位且不会伪装成功；
- 小程序现有装备筛选和展示数据可继续使用；
- 新赛季主要通过修改 `SeasonConfig.lua` 完成升级。

## 18. 斜杠命令异常隔离修复

游戏内 `/wowlook status` 可以执行、而 `/wowlook` 无法清空输入框时，说明命令已经注册并进入处理函数，导出入口在返回前抛出了 Lua 异常。当前已确认的根因是 `tonumber(select(4, GetBuildInfo()))` 将第 4 个及后续返回值全部传给 `tonumber`，导致后续字符串被误作进制参数；并且第 4 个返回值本身是界面版本，真正的客户端 Build 是第 2 个返回值。

修复采用两层保护：

1. 读取 `GetBuildInfo()` 的第 2 个返回值，将构建号接收到独立局部变量后再调用 `tonumber`，导出元数据复用同一读取函数。
2. 斜杠命令通过 `xpcall` 隔离未预期异常，将错误写入 `WoWLookExport3DB.lastError` 并输出到聊天窗口，确保处理函数正常返回、输入框可以清空。

静态测试必须禁止重新出现 `tonumber(select(4, GetBuildInfo()))`，并确认斜杠入口具有异常保护。插件版本升级到 `3.3.2`。
